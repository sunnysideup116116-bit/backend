# Ayue V3 Stages 3–4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Make the canonical Ayue V3 backend safely configurable and expose a stable, tested mobile contract that lets Flutter reproduce the behavior and visual states of the bundled demo website.

**Architecture:** Keep `Server/` intact as the canonical upstream subtree. Put secrets only in ignored per-service environment files, run social and matchmaker in separate Python environments/processes, and add integration-facing documentation or adapters outside the canonical subtree whenever possible. The bundled `frontend.html` is the visual and interaction specification; backend response text is never used as an inferred state machine.

**Tech Stack:** Python 3.12, FastAPI, MongoDB, Neo4j, unittest, NDJSON, Flutter/Dart, Appwrite identity, GitNexus.

## Global Constraints

- New backend logic wins whenever old and new backend behavior conflict.
- Do not casually delete, rename, flatten, or modify files under `Server/`.
- Preserve `social/frontend.html` and its images as the visual reference implementation.
- Before editing a backend function, class, or method, run GitNexus upstream impact analysis and record direct callers, affected processes, and risk.
- Warn before any HIGH or CRITICAL impact edit.
- Record every unavoidable canonical backend modification in `Server/docs/ayue-v3-import-record.md`.
- Never commit secrets or local virtual environments.
- Public Ayue uses V3 and `POST /api/direct_chat/stream`; Private Ayue remains isolated V2.
- Match decisions use canonical state and compare-and-set behavior; clients do not infer match state from prose.
